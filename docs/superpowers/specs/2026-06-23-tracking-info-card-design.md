# Tracking Info Card Design

日期：2026-06-23  
状态：Approved for planning  
范围：DocShop 管理后台追踪日志页（TrackingDashboard）

## 1. 目标

将追踪日志表中的“设备、系统、浏览器、位置、环境”五列合并为一个统一的“访问信息”卡片列，降低表格横向复杂度，提高扫读效率，并通过点击卡片打开详情弹窗的方式承载完整信息与技术字段。

## 2. 用户确认结论

本方案基于以下已确认决策：

- 使用 **单列信息卡片** 替代原五列
- 卡片采用 **标准型摘要**，不是极简折叠卡
- **整个卡片可点击**，点击后打开 **Dialog**
- Dialog 默认优先展示五项核心信息：设备、系统、浏览器、位置、环境
- Dialog 同时补全 **技术信息**，用于排障和数据核查

## 3. 问题背景

当前日志表存在三个直接问题：

1. 表格列过多，核心访问信息被横向打散，浏览效率低
2. 用户要理解一次访问的完整上下文，需要在多列之间来回比对
3. 技术字段缺乏集中展示位置，不利于核查设备解析、浏览器上报和位置信息异常

因此需要将这五类信息聚合成一张信息卡片，并提供可展开的完整细节层。

## 4. 设计目标

### 4.1 主目标

- 将五列信息聚合为一张卡片，提升可读性
- 让用户在列表态即可扫到一次访问的核心画像
- 将完整细节转移到弹窗中，避免表格继续膨胀

### 4.2 次目标

- 保留技术排障所需的原始字段
- 明确空值和回退规则，避免错误展示（如将空坐标显示为 `0.0000, 0.0000`）
- 为后续继续扩展追踪维度保留 UI 容量

## 5. 列表页设计

## 5.1 表格结构调整

在 `TrackingDashboard` 的日志表中，将以下五列删除或并入：

- 设备
- 系统
- 浏览器
- 位置
- 环境

替换为单列：

- **访问信息**

其他列（如时间、IP、访客 ID、请求路径、业务追踪、状态等）保持原有职责，不在本次设计中合并。

## 5.2 信息卡片结构

每一条日志在“访问信息”列中渲染为一张卡片，默认展示四层摘要：

### 第一层：主标题区

展示设备主名称与设备类型标签。

优先级：

1. `device_display_name`
2. `device_brand + device_model`
3. 设备类型回退文案（如“未知手机”“桌面设备”“未识别”）

附加：

- 显示设备类型 tag：desktop / mobile / tablet
- 保持当前追踪展示工具函数的文案风格统一

### 第二层：系统与浏览器区

展示：

- `os_name + os_version`
- `browser_name + browser_version`

格式目标：

- 简洁、一眼可读
- 空字段不拼接脏分隔符

### 第三层：位置区

展示策略：

1. 若 `geo_latitude` 与 `geo_longitude` 都真实存在，显示精确坐标摘要
2. 否则显示 `ip_city + ip_country`
3. 再否则显示“未识别”

约束：

- `null / undefined / ''` 不得被转换成 `0`
- 不允许把缺失位置渲染成 `0.0000, 0.0000`

### 第四层：环境区

展示：

- `client_timezone`
- `client_language`

若为空，则回退为“未识别”或 `-`，保持视觉稳定。

## 5.3 卡片交互

- 整张卡片 hover 时高亮
- 整张卡片点击后打开详情 Dialog
- 不使用单独的“详情”按钮作为主要入口
- 卡片应有可点击态提示（hover、cursor、浅边框/阴影增强）

## 6. Dialog 详情设计

Dialog 标题：**访问信息详情**

顶部放一条摘要头部，用于快速确认当前记录：

- 设备主名称
- 设备类型 tag
- 时间（可复用当前日志时间格式化）

Dialog 内容分成两层。

## 6.1 核心信息层（优先展示）

此层用于日常查看，聚焦五类信息：

### 设备

- 设备主名称
- 设备类型
- 品牌
- 型号

### 系统

- OS 名称
- OS 版本

### 浏览器

- 浏览器名称
- 浏览器版本

### 位置

- 精确坐标
- 精度
- IP 地域

### 环境

- 时区
- 语言

此层应尽量使用描述列表、分组块或两列信息区来组织，而不是简单把所有字段平铺成长列表。

## 6.2 技术信息层（补全展示）

此层用于排障、验数、核查字段映射，需补全以下字段：

- `device_model_code`
- `device_model_name`
- `device_brand_name`
- `device_display_name`
- `screen_resolution`
- `geo_latitude`
- `geo_longitude`
- `geo_accuracy`
- `client_timezone`
- `client_language`
- `user_agent`
- `visitor_id`

展示方式：

- 推荐使用可折叠的“技术信息”区块
- 每个字段展示字段名 + 原始值
- 空值统一显示 `-`

## 7. 数据映射规则

## 7.1 列表卡片使用规则

列表卡片使用已有格式化工具函数作为基础，并扩展为卡片视图数据：

- 设备主名称：沿用 `formatDevicePrimary`
- 系统浏览器摘要：沿用或扩展 `formatDeviceSecondary`
- 位置摘要：沿用并修正 `formatGeoLocation`
- 环境摘要：沿用 `formatClientEnvironment`

## 7.2 Dialog 使用规则

Dialog 不只消费格式化后的字符串，也需要消费原始字段，以便完整展示技术信息。

因此前端实现需要区分两类数据：

1. **摘要型数据**：适合列表卡片
2. **原始字段数据**：适合详情弹窗

## 7.3 空值规则

- 空坐标不得转换为零坐标
- 缺失字符串字段显示 `-` 或“未识别”
- 浏览器/系统组合缺失时不产生多余分隔符
- 技术信息区必须忠实展示原值，不能过度美化到失真

## 8. 组件与实现边界

本次设计优先建议采用以下实现边界：

### 方案

在 `TrackingDashboard.vue` 内新增一个局部的“访问信息卡片 + Dialog”实现，必要时抽出轻量子组件，但避免为了这次改动做过度组件化。

### 原则

- 展示格式逻辑继续集中在 `trackingDisplay.js`
- 页面交互（选中行、打开弹窗、渲染详情）留在 `TrackingDashboard.vue`
- 仅当模板明显膨胀时，再抽取诸如 `TrackingInfoCard` / `TrackingInfoDialog` 子组件

## 9. 测试策略

## 9.1 前端单测

需要覆盖以下行为：

1. 原五列被单列卡片取代后的渲染路径
2. 卡片摘要内容正确
3. 点击整张卡片可打开 Dialog
4. Dialog 中五类核心信息展示正确
5. Dialog 中技术信息展示完整
6. 空值回退正确
7. 缺失坐标时不再显示 `0.0000, 0.0000`

## 9.2 回归验证

重点回归：

- `TrackingDashboard` 现有数据加载不受影响
- 原有 `trackingDisplay` 格式化工具不被其他页面错误破坏
- 页面筛选、刷新、分页、详情打开关闭可以共存

## 10. 非目标

本次设计不包含以下内容：

- 追踪后端字段新增或数据库结构调整
- 新增更多追踪采集维度
- 管理员自定义卡片字段排序
- 卡片拖拽重排
- 对话框内复制按钮、导出按钮等二期增强功能

## 11. 风险与控制

### 风险 1：模板膨胀

如果把卡片与 Dialog 全部硬写在 `TrackingDashboard.vue` 中，文件会继续变大。

控制：

- 优先局部实现
- 如果模板明显失控，再抽取轻量子组件

### 风险 2：格式化逻辑重复

若卡片与 Dialog 各自写一套文案逻辑，后期容易漂移。

控制：

- 复用 `trackingDisplay.js` 中已有摘要函数
- Dialog 原始值展示与摘要展示职责分离

### 风险 3：空值和技术值混用

若把“用户可读摘要”和“技术原始字段”混在一起，会出现既不好看也不利于排障的情况。

控制：

- 列表只看摘要
- Dialog 分层：核心信息 + 技术信息

## 12. 验收标准

满足以下条件视为设计落地成功：

1. 日志表中五列合并为一个“访问信息”卡片列
2. 卡片默认能稳定展示设备、系统/浏览器、位置、环境摘要
3. 点击整卡能打开详情 Dialog
4. Dialog 同时展示核心信息与补全后的技术信息
5. 缺失地理位置时不再出现 `0.0000, 0.0000`
6. 页面整体横向可读性明显优于当前五列拆散方案
